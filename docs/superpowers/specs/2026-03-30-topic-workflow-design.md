# 2026-03-30 选题池闭环设计

## 目标

把当前原型从“内容浏览 + 临时勾选分析”升级成完整的选题监控闭环：

1. 在分类下配置监控平台、关键词、对标博主
2. 手动触发采集，把不同平台的文章拉入内容池
3. 用户手动新建“选题卡片”作为工作对象
4. 从内容池把不同平台文章归集进某个选题
5. 基于该选题下的文章集合执行两阶段 AI 分析
6. 输出可追溯、可复查的结构化选题洞察报告

## 现状问题

当前页面已经有内容池、公众号同步、AI 报告能力，但逻辑没有真正闭环：

- `监控设置` 只能展示，不能新增或编辑关键词、博主、平台配置
- `内容` 页能浏览内容，但只能临时把内容标记为“加入选题分析”
- `选题分析与报告` 直接分析临时勾选结果，没有正式的“选题对象”
- 首页公众号搜索与分类监控仍然是两套入口
- 数据主要停留在前端内存中，刷新后状态会丢失

## 设计原则

- 以“选题卡片”而不是“文章勾选状态”作为核心对象
- 让运营先定义选题，再归集素材，再做 AI 分析
- 保留现有时间轴、内容池、平台筛选等高价值结构
- 第一版优先打通流程，不引入复杂后端服务
- 持久化优先采用本地轻量存储，方便原型阶段快速验证

## 方案选型

### 方案 A：仅前端状态

优点：实现最快。
缺点：刷新后丢失数据，无法形成真实工作流。

### 方案 B：本地文本缓存（JSON）

优点：实现简单、调试容易、适合原型。
缺点：并发和结构演进能力一般。

### 方案 C：SQLite 本地缓存（推荐）

优点：
- 比 JSON 更适合保存选题、文章、分析结果之间的关系
- 后续更容易扩展成历史报告、分析记录、手动备注
- 适合 Next.js 原型阶段的本地持久化

缺点：
- 需要新增最小数据访问层

推荐：
- 第一优先用 SQLite
- 如果当前环境接 SQLite 成本过高，则先落 JSON 文件缓存，并把数据访问层抽象出来，后续可平滑切换到 SQLite

## 核心对象设计

### 1. MonitorCategory

保留现有分类对象，继续作为顶层隔离单元。

### 2. TopicCard

新增正式的选题对象：

- `id`
- `categoryId`
- `title`
- `description`
- `goal`
- `status`：`draft | collecting | ready | analyzed`
- `keywords`：选题关注词，可选
- `sourceArticleIds`
- `createdAt`
- `updatedAt`
- `lastAnalysisAt`

说明：
- `title`：选题名称
- `description`：为什么建这个选题
- `goal`：希望解决的内容目标，例如“做公众号长文”“做短视频对比测评”
- `sourceArticleIds`：归集到该选题下的内容 ID

### 3. ContentItem

保留现有内容池对象，并增加可追踪字段：

- `id`
- `categoryId`
- `platform`
- `title`
- `summary`
- `creator`
- `matchedKeywords`
- `matchedCreators`
- `topicIds`：该内容被加入了哪些选题
- `sourcePayload`：原始接口必要信息，可选

### 4. TopicAnalysisResult

分析结果与选题绑定，而不是与页面绑定：

- `topicId`
- `generatedAt`
- `model`
- `articleInsights`
- `topicInsights`

## 完整业务流程

### 流程 1：配置监控范围

1. 用户进入某个分类的 `监控设置`
2. 开启或关闭平台
3. 新增多个关键词
4. 新增多个对标博主
5. 点击 `保存设置`

结果：
- 当前分类的采集配置被持久化

### 流程 2：采集内容

1. 用户在 `监控设置` 或 `内容` 页点击 `同步数据`
2. 系统按分类下的关键词逐个请求采集接口
3. 采集结果统一映射成 `ContentItem`
4. 合并进该分类的内容池
5. 更新最近同步时间、同步状态、同步数量

测试阶段限制：
- 单次公众号拉取最多保留 10 条

### 流程 3：新建选题

1. 用户进入 `内容` 或 `选题分析与报告`
2. 点击 `新建选题`
3. 填写：
   - 选题标题
   - 选题简介
   - 目标
4. 创建成功后，生成一张独立选题卡片

### 流程 4：归集文章到选题

1. 用户在 `内容` 页浏览内容池
2. 点击某条内容的 `加入选题`
3. 选择已有选题，或当场新建选题
4. 系统把文章 ID 关联到该选题的 `sourceArticleIds`
5. 内容卡显示其所属选题标签

### 流程 5：执行 AI 分析

1. 用户进入 `选题分析与报告`
2. 先选择一个选题卡片
3. 系统展示该选题下已归集的文章
4. 用户点击 `开始 AI 分析`
5. 后端对当前选题执行两阶段分析：
   - 阶段一：逐篇结构化摘录
   - 阶段二：聚合生成至少 5 条选题洞察
6. 分析结果保存并绑定到该选题

### 流程 6：查看报告

用户在同一选题下看到：
- 本次分析时间
- 使用模型
- 单篇文章结构化摘录
- 至少 5 条结构化选题洞察
- 每条洞察所引用的文章

## AI 分析设计

### 输入范围

只分析“当前选题下已归集的文章”，不直接分析全量内容池。

### 阶段一：单篇摘录

每篇文章输出：
- 标题
- 摘要
- 关键信息
- 关键词
- 亮点
- 爆点/钩子
- 内容角度
- 平台适配建议

### 阶段二：聚合洞察

至少输出 5 条结构化选题洞察，每条包括：
- 方向标题
- 选题简介
- 为什么值得做
- 增长空间在哪里
- 亮点拆解
- 建议平台
- 关联文章

## 错误处理

### 采集失败
- 显示关键词级失败提示
- 保留已成功采集内容
- 不阻断整个分类工作台

### 选题无内容
- 禁止执行 AI 分析
- 提示先去内容池归集文章

### AI 分析失败
- 保留上一次分析结果
- 显示本次失败原因
- 支持重新分析

## 推荐实施顺序

1. 抽出本地存储层（优先 SQLite，备选 JSON）
2. 把 `监控设置` 改成可编辑可保存
3. 引入 `TopicCard` 数据模型
4. 改造内容池操作为“加入选题”
5. 改造报告页为“按选题分析”
6. 接通分析结果持久化
7. 做细节提示和错误处理

## 本次推荐结论

推荐采用：
- `选题卡片` 作为核心对象
- `SQLite` 作为第一选择的本地缓存方案
- 如果当前依赖接入成本较高，先用 `JSON` 文件缓存，但必须抽象统一存储层

这样可以在不推翻现有原型的前提下，把“关键词配置 -> 数据采集 -> 内容入池 -> 选题归集 -> AI 洞察”完整闭环打通。
